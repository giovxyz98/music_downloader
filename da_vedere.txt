SEZIONE B — PROBLEMI ARCHITETTURALI (da valutare in futuro)
════════════════════════════════════════════════════════════════

1. Classe troppo grande

MusicDownloaderApp ha troppe responsabilità:
UI, orchestrazione download, pipeline workers,
cache orchestration, navigazione, business logic.

Consigliato separare in:
DownloadManager, SearchController, QueueManager, UIController

2. Troppa logica nei callback UI

Esempio: _download_albums_batch fa API + filesystem + queue building + UI.
Dovrebbe delegare.

3. Mancanza rate limiting API

Se l'utente fa molte ricerche rapide (search_artist, search_track,
get_album_tracks, get_album_details) rischia di saturare l'API Deezer.
Meglio aggiungere Semaphore o RateLimiter.

4. Cache in-memory senza limite

self._genre_cache e self._nb_tracks_cache crescono senza limite.
Meglio LRU cache con max size.

5. Possibile memory leak widget

In _show_download_panel:
    for w in self.queue_panel.winfo_children(): w.destroy()
Funziona ma molte ricreazioni possono frammentare la UI.
Meglio riusare alcuni widget.

6. Piccola inefficienza nella queue

Controllo duplicati con any(item.query == query ...) è O(n).
Meglio tenere un set di query parallelo.
